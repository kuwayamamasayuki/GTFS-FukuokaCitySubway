# 博多駅の二駅モデル（空港線博多 / 七隈線博多）— Issue #53

## 背景と目的

空港線博多駅と七隈線博多駅は、駅名こそ同じ「博多」だが**物理的に少し離れた別の駅**であ
る。地図上でも別々の駅マーカーとして表示されるべきなので、七隈線博多に空港線博多とは
**異なる緯度経度**を与えたい、というのが Issue #53 の要件である。

一方で、両者は**運賃計算上は同一の駅（同一運賃ゾーン）**として扱う必要がある。

## 採用したデータモデル

`reference_gtfs/stops.txt` で博多を次の **2 つの親駅（location_type=1）** に分けて表現する。

| stop_id | stop_code | 役割 | 座標 | zone_id |
|---|---|---|---|---|
| `11`   | `K11/N18` | 空港線博多（＋名前解決・ジャンクションの担い手） | 空港線位置 `33.59013, 130.420616` | `11` |
| `11_1` / `11_2` | — | 空港線ホーム（parent=11） | 空港線位置 | `11` |
| `37`   | `N18`     | **七隈線博多（独立駅マーカー）** | 七隈線位置 `33.589616, 130.418599` | `11` |
| `37_3` / `37_4` | — | 七隈線ホーム（parent=37） | 七隈線位置 | `11` |

- 七隈線博多は独立した親駅 `37` として別座標を持つ → 地図上で別マーカーになる（要件達成）。
- すべて `zone_id=11` → 運賃ゾーンは空港線博多と同一（運賃計算は不変）。
- 旧モデルにあった `11_3` / `11_4`（11 配下の七隈線ホーム）は廃止した。

座標出典: OpenStreetMap（七隈線博多駅ホーム付近）。

## なぜ非対称なのか（重要）

「完全に対称」なら `11=K11`（空港線博多）／`37=N18`（七隈線博多）と分けたいところだが、
**あえて `11` の stop_code を `K11/N18` のまま据え置いている。** 一見すると「11 が N18 も
名乗っているのに七隈線ホームは 37 配下」という不整合に見えるため、理由を明記する。

理由は `StationMapper`（`src/fukuoka_gtfs/station_mapper.py`）の解決順序にある。

1. Excel の時刻表をパースする際、各駅セルは `mapper.parent_id(駅名)` で **駅名→親 id** に
   解決される。この時点では**そのトリップがどの路線かはまだ分からない**。
2. 路線の判定は後段の `split_segments()` が、停車駅の集合から行う。共用駅
   （複数路線を兼ねる駅 = `single_line()` が `None`）はセグメントの**境界**として扱われる。

ここで「博多」という駅名は空港線トリップにも七隈線トリップにも現れる。`parent_id("博多")`
は単一の親 id を返さねばならないため、**その親は両路線を兼ねるジャンクションでなければ
ならない。**

もし `parent_id("博多")` が七隈線専用の `37` を返すと:

- **空港線トリップ**の終点 博多 が七隈線駅に解決され、`platform(37, 空港線, dir)` が
  存在しないホームを参照して**空港線トリップが壊れる**。
- **純七隈線トリップ**（例: 橋本→…→櫛田神社前→博多）でも、博多が「七隈線専用」だと
  `split_segments` が末端を別セグメント扱いし、**博多停車がドロップされる**おそれがある
  （博多が `single_line=None` の共用駅であることがこの停車を支えている）。

そこで:

- `11` を `K11/N18`（2 路線＝ジャンクション）のまま残し、**「博多」の名前解決先**かつ
  **ジャンクション**の役割を担わせる。
- 七隈線ホームだけを独立駅 `37` 配下（`37_3`/`37_4`）に移し、別座標を与える。
- `config/stations.yaml` の `platform_overrides` で、**親キー `11` のまま** 七隈線方向に
  `37_3`/`37_4` を返すよう対応付ける。これで名前解決は `11`、ホームは `37` 配下、という
  役割分担が成立する。

```yaml
# config/stations.yaml
"11":
  空港線: {0: "11_1", 1: "11_2"}
  七隈線: {0: "37_3", 1: "37_4"}   # ← 親キーは 11、返すホームは 37 配下
```

## 同名親の名前解決ルール

`StationMapper.from_stops()` は、**同名の親駅が複数あるとき、所属路線数が最も多い
（＝共用ジャンクションの）親を名前解決先に採用する。** 博多なら `11`（2 路線）が `37`
（1 路線）に勝つ。このルールは `stops.txt` の行順に依存しない。

```python
prev = parent_by_name.get(name)
if prev is None or len(lines) > len(lines_by_parent.get(prev, set())):
    parent_by_name[name] = sid
```

この前提を守るため、**`37` の stop_code は `N18` のみ**にしている。仮に `37` も
`K11/N18`（2 路線）にすると `11` と路線数が同点になり、名前解決先が不定（順序依存）に
なって空港線トリップが壊れうる。`K11` は空港線博多の駅番号なので、七隈線側の `37` が
名乗るのも意味的に誤りである。

## 中洲川端との違い

中洲川端（id 9, `K09/H01`）も同名で 2 路線を持つが、**2 路線が物理的に同じ場所**にある
ため、親は 1 つ（id 9）のままで子ホーム 9_1〜9_4 がすべて同座標、という単純なモデルで
足りる。博多は 2 路線が**別の場所**にあるため、独立駅マーカー（id 37）を追加した点が
異なる。

## 完全分離（11=K11 / 37=N18）にしなかった理由

完全分離するには、`parent_id()` を「トリップの路線文脈ありで 2 パス解決する」など
`StationMapper` / `train_extractor` の中規模リファクタが必要で、博多停車ドロップ等の
回帰リスクも上がる。要件（七隈線博多を別座標の独立マーカーにする）は本モデルで満たせる
ため、変更を `stops.txt` + `stations.yaml` + `from_stops` の同名解決 3 行に限定した。
